# ИИ-Мастер — текстовая RPG по D&D 2024 с ИИ-ведущим

Веб-игра: текстовая ролевая игра по правилам D&D 2024 (SRD 5.2). Роль ведущего (Мастера)
исполняет Claude через Anthropic API.

## Стек

- Vite + React + TypeScript.
- **Без бэкенда.** Весь код работает в браузере игрока.
- Сайт статический, публикуется на GitHub Pages (`https://<user>.github.io/dnd_ai_master/`).

## Архитектура: код — правила, ИИ — рассказ

Главный принцип: **код — единственный источник истины о состоянии игры.**

- **Код отвечает за:**
  - правила SRD 5.2 (проверки, спасброски, атаки, урон, отдых, условия и т. д.);
  - броски кубиков (только в коде, с честным ГСЧ; ИИ не «придумывает» результаты) —
    модуль `src/engine/dice.ts`: запись `1d20+5`, `4d6kh3`, преимущество/помеха, подробный результат.
    Все случайные числа игры — только через него; в тестах генератор подменяется (`rng`);
  - правила проверок — `src/engine/`: `abilities.ts` (характеристики, модификаторы, бонус мастерства),
    `skills.ts` (18 навыков, владение и компетентность), `conditions.ts` (15 состояний и их влияние на
    броски к20), `checks.ts` (`abilityCheck`, `savingThrow`, `passivePerception`, `formatD20Test`).
    Проверка возвращает подробный результат: режим и его причины, разбивку модификатора, бросок, успех.
    В SRD 5.2 натуральные 20/1 не дают автоуспеха/автопровала проверкам и спасброскам — только атакам;
  - состояние игры: персонаж, характеристики, хиты, инвентарь, текущая локация, флаги сюжета.
- **ИИ-ведущий отвечает за:**
  - повествование и описание сцен, реплики НПС;
  - решение, *когда* нужна проверка (какой навык/характеристика, какая Сл) — в виде
    структурированного запроса, который код валидирует и исполняет.
- **ИИ никогда не меняет состояние напрямую.** Он может только *предлагать* действия
  (например, через tool use / структурированный JSON-ответ: «запроси проверку Ловкости (Скрытность) Сл 15»,
  «предложи передать предмет X»). Код проверяет запрос по правилам и текущему состоянию,
  применяет его сам и сообщает ИИ результат для дальнейшего рассказа.
- **Игра состоит из независимых историй (кампаний).** Все игровые данные **всегда принадлежат конкретной истории**:
  отряд героев (`party` — список, код не должен рассчитывать, что герой один), мир (`world`: собственные копии локаций,
  двери, НПС, факты, квесты), журнал приключения, лог сообщений и бросков. Тип — `StoryState` (`src/types/story.ts`).
  Истории не смешиваются: ничто из одной истории не читается и не меняется из другой.
- **Состояние истории меняется только через действия** (`StoryAction`): тип, автор (`player` с героем, `engine`, `master`,
  `system`) и время — «игрок сказал», «движок бросил кубик», «ведущий переместил НПС». Состояние — применение действий
  по порядку (`applyAction`/`replay` в `src/game/storyActions.ts`); применение детерминировано, всё случайное (id, броски,
  время) записано в самом действии. Перед записью действие проверяется по правилам (`checkAction`). Журнал действий
  хранится целиком — задел под мультиплеер (действия можно будет передавать между игроками).
  Новое изменение состояния = новый тип события в `StoryEvent` + ветка в `applyEvent` + проверка в `checkAction` + тест.
- **Хранение — IndexedDB через Dexie** (`src/game/repository.ts`, база `ai-master`): `stories` (сведения для списка),
  `actions` (журнал, ключ `[storyId+seq]`), `snapshots` (кэш последнего состояния; если он отстал — журнал воспроизводится),
  `heroes`, `hall`. localStorage только для мелочей интерфейса (выбранная вкладка) и отладочного флага.
  Хранилище приложения — `src/game/appStore.ts` (экземпляр `src/game/appInstance.ts`, в React — `useAppState()`):
  открытая история, команды (`createStory`, `dispatch`, `dispatchTo`, `renameStory`, `deleteStory`, `completeActive`,
  герои), запись в базу строго по очереди (`flush` — дождаться записи).
  Старое сохранение из localStorage (`ai-master:save` v1–8 и `ai-master:heroes`) переносится при запуске
  (`src/game/legacyImport.ts`, миграции старого формата — `legacySave.ts`/`legacyState.ts`), копия — `ai-master:legacy-backup`.
  При несовместимом изменении `StoryState` — менять формат так, чтобы старые журналы воспроизводились (или переносить их).
- Экраны: «Мои истории» (`StoriesScreen`: продолжить, новая, переименовать, удалить с подтверждением), «Новая история»
  (`NewStoryScreen`: свободный герой или новый, название, тон — тёмное фэнтези / лёгкое приключение / детектив / хоррор,
  приключение). Название и тон попадут в системный промт ведущего. Приключения — `src/data/adventures/`
  (локации, стартовая локация, вступление, тон по умолчанию); таверна «Пьяный грифон» — по умолчанию.
- Логику правил держать чистыми функциями, отдельно от React-компонентов и от слоя работы с API,
  чтобы её было легко тестировать.

## Данные игры — в JSON

- Все игровые данные (локации, предметы, НПС, а позже — монстры, заклинания и т. п.)
  хранятся в JSON-файлах (`src/data/`), а не захардкожены в коде.
- Для каждого типа данных — TypeScript-тип и валидация при загрузке.
- Локации: формат описан в `docs/location-format.md`, типы — `src/types/location.ts`,
  валидация — `parseLocation` в `src/game/location.ts`, файлы — `src/data/locations/`.
  При изменении формата обновлять документ: по нему ИИ будет генерировать локации.
  Стены **тонкие** — отрезки по границам клеток (как в Roll20/Foundry); клетка — только пол или пустота.
  Двери (`open`/`closed`/`locked`) и окна — отрезки на стенах.
  Локации из `src/data/locations/` — шаблоны: при создании истории они копируются в её мир, и дальше НПС, двери и т. п.
  меняются действиями только в этой истории. Упрощённая запись для генерации: комнаты-прямоугольники
  `rooms` (стены по периметру — автоматически), перегородки `walls`, проёмы `openings`; `parseLocation` приводит всё
  к полной записи (`floorPlan` + единичные стены) и проверяет: двери/окна только на стенах, весь пол достижим от входа
  `playerStart`, объекты и НПС на полу. Текущее состояние дверей — в мире истории (`world.doors`).
  Проходимость и линия видимости — `src/engine/movement.ts` (`canStep`/`stepBlocker`, `hasLineOfSight`):
  нельзя сквозь стену/окно/закрытую дверь и по диагонали между углами стен.
- Предметы: справочник `src/data/items.json` (типы — `src/types/items.ts`, валидация — `src/game/items.ts`).
  Инвентарь хранит только `itemId` и количество, свойства предмета берутся из справочника.
  У предметов есть цена `cost` в зм (без цены — не купить), у оружия `weapon.kind` (simple/martial),
  у инструментов `toolKind` (artisan/gaming/musical/kit); владение инструментами — `proficiencies.tools`.
  Владение доспехами — `proficiencies.armor` (light/medium/heavy/shield, из `armorTraining` класса). КД — `armorClass`
  в `src/game/character.ts`: щит без владения щитами не даёт КД (SRD 5.2); в справочнике все 12 доспехов SRD и щит.
- Экипировка — руки: `{ mainHand, offHand, armor }`. Правила (двуручное, щит, два лёгких оружия, объяснение
  отказа) — `src/game/equipment.ts`, атаки оружием (бонус, урон, боевые стили) — `src/game/attacks.ts`.
  Смена экипировки — `equipmentEvent` (правила) → действие `equipmentChanged` героя в истории.
  Вне боя смена свободная; ограничения в бою появятся с боевой системой.
- Персонажи: `src/data/characters/` (типы — `src/types/character.ts`, правила и валидация — `src/game/character.ts`).
  Производные величины (КД, модификаторы, грузоподъёмность) не хранятся, а считаются кодом.
- Создание персонажа (SRD 5.2): классы, предыстории, виды, черты происхождения и наборы снаряжения —
  `src/data/rules/*.json` (типы — `src/types/rules.ts`, проверка ссылок на навыки/предметы — `src/game/rulesData.ts`).
  Логика мастера — чистые функции `src/game/creation.ts` (`stepProblems`, `finalScores`, `buildCharacterSheet`…),
  UI — `src/components/creation/`. В данных только то, что есть в SRD 5.2.
  Черты: `category` origin (черты происхождения) или fighting-style (боевые стили Воина, с эффектами в правилах).
- Шаблон предыстории 2024 (3 характеристики, 2 навыка, инструмент, черта происхождения, снаряжение ≤ 50 зм) —
  `validateBackgroundTemplate` в `src/game/backgroundTemplate.ts`. Им проверяются официальные предыстории,
  «Своя предыстория» игрока и (в будущем) предыстории, предложенные ИИ.
- При запуске всегда открывается стартовый экран (`src/components/StartMenu.tsx`): «Продолжить» (последняя незавершённая
  история), «Мои истории», «Мои герои», «Создать нового героя», «Быстрый старт (Ратибор)» — новая история за Ратибора,
  а если он уже в истории — продолжить её. В шапке игры — «Завершить историю» и «В меню».
  Готовый персонаж Ратибор (`src/data/characters/`) — e2e-тесты входят в игру через `startQuickGame`.
- «Мои герои» и «Зал славы»: герой (его исходный лист) принадлежит игроку, его состояние в игре — отряду истории.
  Правила — чистые функции `src/game/heroes.ts` (добавить, переименовать, удалить, вступить в историю/выйти, `retireHero`
  с итогом пути), UI — `src/components/HeroesScreen.tsx`. Один герой — только в одной незавершённой истории; героя
  в истории удалить нельзя; при удалении истории её герои возвращаются в список с тем, что получили в ней.
  Погибшие (`fallen`) и герои завершённых историй (`completed`) уходят в «Зал славы». При загрузке список согласуется
  с историями (`reconcileRoster`).
- Формат должен быть простым и самодостаточным, чтобы в будущем ИИ мог генерировать
  новые локации/предметы/НПС в том же формате, а код — валидировать их перед использованием.

## Ключ API

- Бэкенда нет, поэтому ключ Anthropic API вводит сам игрок в настройках.
- Ключ хранится **только в браузере игрока** (localStorage) и отправляется только напрямую в Anthropic API.
- Никогда не коммитить ключи, не вшивать их в сборку, не отправлять на сторонние сервисы и не логировать.

## Интерфейс

- Весь интерфейс и все тексты для игрока — **на русском языке**.
- ИИ-ведущий тоже ведёт игру на русском.

## Сборка и публикация

- `npm run dev` — локальная разработка.
- `npm run build` — проверка типов и сборка в `dist/`.
- `npm run lint` — линтер (oxlint).
- `npm test` — тесты (Vitest), `npm run test:watch` — в режиме наблюдения. Тесты лежат рядом с кодом: `*.test.ts`.
  Логику правил и валидаторы данных покрывать тестами.
- `npm run test:e2e` — e2e-тесты Playwright (`e2e/*.spec.ts`) на собранном сайте: сначала `npm run build`.
  Два проекта: `desktop` (1440×900) и `mobile` (iPhone 13 на Chromium). Сайт отдаёт `e2e/serve.mjs`
  по пути `/dnd_ai_master/`, как GitHub Pages. Случайность в e2e подменяется через `installRngQueue`/`queueRolls`.
  Новые элементы интерфейса покрывать e2e-тестами, на телефоне проверять отсутствие горизонтальной прокрутки.
  Импортировать `test`/`expect` из `e2e/fixtures.ts`: на телефоне он подставляет широкий шрифт (DejaVu Sans),
  как в CI и на Android, — с узким локальным шрифтом переполнение по ширине не видно. Фикстура включает отладочный доступ
  `window.__aiMaster` (флаг localStorage `ai-master:debug`): состояние меняется не правкой хранилища, а действиями —
  `act(page, событие, MASTER/ENGINE)`; перед перезагрузкой — `flushSaves` / `reloadAndContinue`.
  Модульные тесты IndexedDB — через `fake-indexeddb` (`import 'fake-indexeddb/auto'`), у каждого теста своя база.
- `base` в `vite.config.ts` при сборке равен `/dnd_ai_master/` (имя репозитория) — нужно для GitHub Pages.
  При переименовании репозитория обновить `REPO_NAME`.
- `.github/workflows/deploy.yml` прогоняет модульные тесты, собирает сайт, прогоняет e2e-тесты и только при их успехе
  публикует сайт на GitHub Pages (при каждом пуше в `main`). При падении e2e отчёт Playwright сохраняется
  как артефакт `playwright-report`.
  В настройках репозитория: Settings → Pages → Source = **GitHub Actions**.

## Рабочий процесс

- **После каждой завершённой задачи делать коммит и пуш.**
- Перед коммитом убедиться, что `npm test`, `npm run build` и `npm run test:e2e` проходят без ошибок.
